# Конфиденциальность и безопасность BoneQC

## Назначение

BoneQC работает с медицинскими DICOM-файлами, поэтому обработка данных должна учитывать конфиденциальность, минимизацию данных и разделение доверенных контуров.

## Основные принципы

Для проекта используются следующие принципы:

- минимизация сохраняемых персональных данных;
- деидентификация до передачи в ML-контур;
- ограничение доступа по ролям;
- разделение product, expert и frozen ML данных;
- отсутствие production secrets в Git;
- fail-safe поведение при невозможности безопасной обработки.

## Проверка DICOM

До дальнейшей обработки проверяется возможность корректно прочитать входной DICOM.

Повреждённый или неподдерживаемый файл не должен автоматически интерпретироваться как PASS.

## Деидентификация metadata

Перед использованием подготовленного исследования в ML-контуре выполняется удаление или замена идентифицирующих DICOM metadata.

В частности, используются:

- удаление ненужных идентифицирующих полей;
- замена внутренних идентификаторов;
- UID remapping;
- минимизация сохраняемой metadata.

## Private DICOM tags

Private tags рассматриваются отдельно, поскольку могут содержать данные производителя или идентифицирующую информацию.

Неизвестные private tags не должны автоматически считаться безопасными для публикации.

## Pixel Data

Удаление DICOM metadata не гарантирует удаления информации, уже встроенной в само изображение.

Отдельный риск представляют:

- burned-in annotations;
- текст внутри pixel data;
- визуально распознаваемые идентификаторы.

Этот риск должен рассматриваться отдельно от metadata de-identification.

## Preview

Preview используется для интерфейса.

Preview не является ML input frozen C7.

Публикация preview должна подчиняться тем же ограничениям конфиденциальности, что и исходное медицинское изображение.

## Object Storage

Object Storage относится к внутреннему trusted contour.

Он не должен предоставлять анонимный публичный доступ к медицинским объектам.

Доступ к файлам должен проходить через контролируемый application layer.

## PostgreSQL

PostgreSQL содержит служебные и пользовательские данные продукта.

База данных не должна публиковаться напрямую в интернет.

## Redis

Redis является внутренним инфраструктурным сервисом.

Он не должен быть публичным endpoint.

## RBAC

Основные роли:

~~~text
ADMIN
OPERATOR
DOCTOR
~~~

Авторизация и проверка доступа выполняются на backend, а не только в пользовательском интерфейсе.

## Разделение автоматического и экспертного контуров

Automatic C7 result и экспертная разметка хранятся отдельно.

Это необходимо для того, чтобы экспертная оценка:

- не подменяла автоматический результат;
- не изменяла frozen model;
- не приводила к неявному переобучению.

## Secrets

Реальные секреты не должны храниться в Git.

К ним относятся:

- пароли;
- токены;
- session secrets;
- gateway credentials;
- приватные ключи.

Для репозитория используются только безопасные шаблоны конфигурации.

## Environment files

Файлы с реальными environment values должны иметь ограниченные права доступа и не должны попадать в публичный репозиторий.

## Логи

Логи не должны намеренно включать:

- ФИО пациента;
- исходные медицинские идентификаторы;
- DICOM UID, если они позволяют восстановить чувствительные связи;
- секреты;
- токены доступа.

## Audit trail

Критичные действия системы и пользователей должны фиксироваться отдельно от обычных application logs.

Audit trail предназначен для отслеживания действий, а не для хранения полного содержимого медицинских объектов.

## Network exposure

Во внешний контур публикуются только сервисы, необходимые пользователю.

Внутренние БД, очереди, object storage и ML endpoints не должны быть напрямую доступны из интернета без отдельной необходимости.

## Frozen C7 security boundary

Competition runtime использует локальные frozen model artifacts.

Во время inference:

- веса не скачиваются из сети;
- модель не изменяется;
- thresholds не изменяются;
- внешние AI API не требуются.

## Fail-safe behavior

Если файл невозможно безопасно или корректно обработать, система должна вернуть ошибку или `CANNOT_ASSESS`.

Нельзя подменять невозможность оценки автоматическим PASS.

## Data minimization

Храниться должны только данные, необходимые для:

- работы сервиса;
- воспроизводимости результата;
- аудита;
- разрешённых экспертных сценариев.

## Retention

Срок хранения медицинских и служебных данных зависит от режима эксплуатации и политики организации.

Публичный конкурсный репозиторий не задаёт универсальную медицинскую retention policy.

## Backups

Для stateful production deployment должна существовать отдельная backup/restore стратегия.

Backup медицинских данных требует тех же мер защиты, что и основной storage.

## Public repository boundary

В публичном репозитории не должны находиться:

- реальные медицинские DICOM;
- production secrets;
- приватные ключи;
- персональные данные пациентов;
- закрытые внутренние credentials.

## Compliance boundary

BoneQC является исследовательским прототипом.

Документация проекта не заявляет соответствие конкретному медицинскому регламенту, сертификации или статус зарегистрированного медицинского изделия.

## Clinical boundary

Меры безопасности данных не изменяют назначение BoneQC: система выполняет технический QC и не ставит диагноз.
